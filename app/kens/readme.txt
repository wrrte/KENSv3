이전과 달리 연결을 지속해야 하므로, 소켓에 connected 항목을 추가한다.
패킷이 오면 소켓 테이블에서 연결이 된 소켓을 먼저 검사하는 부분을 추가하여, 연결이 이미 수락된 소켓이 있다면 그걸로 통신하도록 한다.

read. 생각보다 쉽다
보통은 패킷보다 application으로부터 read 명령이 먼저 온다. 
그럼 syscallUUID, buf, count를 저장해둔다.
패킷이 도착하고 그게 데이타 패킷이라면, 그냥 buf에다가 집어넣고 반환하면 끝.
문제는 buf의 크기가 매우 작을 경우에는 여러번의 read 호출로 하나의 패킷을 읽어야 한다.
이 경우에는 read buffer에다가 집어넣고 조금씩 꺼내 읽으면 된다.

write. 엄청 짜증난다. (조교님의 도움에 감사를 표하자.)
기본적으로는 read랑 비슷하게, 그냥 역순으로 하면 된다.
그리고 rwnd가 꽉 차면 send buffer에 집어넣고 역시 read처럼 조금씩 꺼내 읽으면 된다.
여기서 send buffer가 딱 send_base가 index 0인 window와 같다. 
window 그림에서 ack이 오면 send base가 우측으로 이동하듯이, 기존 send base에서 새 send base 부분의 데이터를 보내고 비우면 된다.
application으로부터 write 명령이 왔을 때 rwnd가 안 찼으면 그냥 보내고 nextseqnum을 증가시키면 되고, 
꽉 찼으면 send buffer에 넣고 잊어버리면 나중에 ack이 도착하여 send_buffer가 이동했을 때 자동으로 데이터를 보내면 된다.
(이 때 중요한 점이 close에서 바로 소켓을 없애버리면 나중에 소켓이 사라져서 소켓 내부의 send buffer의 데이터를 못 찾기 때문에, 
close 여부를 확인하여 send_buffer가 비워지면 소켓 테이블에서 제거해야 한다.)

타이머를 사용한 unreliable 검사도 의외로 간단?하다?
타이머를 add 할 때 payload에 패킷도 통채로 집어넣어서 시간 다 되면 패킷을 다시 보내고, 
곳곳에 (synack queue라든가 등등 ) 저장해둔 timerkey의 값을 갱신해주면 된다.
그리고 제대로 보냈다는 응답이 왔으면 타이머 꺼내서 취소하면 되고.
그리고 데이터에 대한 응답으로 보낸 ack 패킷이 유실되면 내가 예상하는 다음 데이터 이전 데이터를 상대가 또 보내기 때문에,
이전 데이터를 받았다면 이전 ack을 그냥 한 번 더 보내주면 해결.
